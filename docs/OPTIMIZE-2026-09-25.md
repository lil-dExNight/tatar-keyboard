# OPTIMIZE-2026-09-25 — the SAFE optimization wave

A wave of zero-quality-loss optimizations: dead-resource removal, startup-path savings,
engine micro-optimizations, memory and render/battery work. Every item was applied only
after its claim was re-verified in the tree; behavior is byte-identical except where an
item says otherwise. No commits (the operator commits).

Gates at the end of this document. Analyzer references are the mission brief's file:line
findings, each re-verified before editing; where the re-verification disagreed with the
brief, the deviation is stated.

## Applied

### 1. Dead string `icon_launcher_text` deleted
- **What**: `app/src/main/res/values/icons.xml` held the legacy "Simple" launcher-icon glyph
  path data (~1.7 KB of path text). Zero references anywhere in `app/src` (verified by grep:
  only the definition itself, the lint baseline entry, and the lint.xml classification
  comment mentioned it).
- **Why**: dead weight in `resources.arsc` and the DEX string table.
- **Bytes**: −1 690 B raw resource text (arsc-level delta smaller after compression).
- Analyzer finding: `values/icons.xml:19`, confirmed.

### 2. Dead style `AppText.Button` deleted

  styles are used by the settings screens; `AppText.Button` never was).
- **Bytes**: −4 arsc entries (style + 2 items + name).

### 3. Unused 5-row fractions deleted

- **Effect**: the two live lint warnings are gone (6 → 4 live warnings; see Gates).

### 4. Lint baseline cleaned

  moot by items 1–2, and the `AndroidGradlePluginVersion` entry lint itself flagged as

### 5. `Settings.readKeyboardColor`: default computed lazily
- **What**: `Settings.java:494` was `prefs.getInt(PREF_KEYBOARD_COLOR,
  readKeyboardDefaultColor(context))` — the default (a walk over the theme table and the
  colour resource arrays) was computed on EVERY read, then thrown away whenever the
  preference held a value. Now `prefs.contains(PREF_KEYBOARD_COLOR)` gates the walk.
- **Behavior**: identical. `getInt` on a non-int value throws ClassCastException in both
  versions; the `0` fallback in the contains-branch is unreachable-by-construction.
- **Pin**: new `KeyboardColorPreferenceTest` (source-contract style, like the other settings
  tests — the JVM suite runs without Robolectric): stored value branch, default branch, and
  their order (contains → getInt → default).
- **ms**: one theme-table walk + two int-array resource reads saved per call on the
  settings/keyboard-color path once the user (or an MDM restriction) has set a color.

### 6. `startup-prof.txt` regenerated
- The file predated the phase-6 splits: zero `LatinIme*` and zero glide (`GlidePath`,
  `GlideDecoder`, `GlideTrail`) rules (verified: 0/0 against baseline-prof.txt's 11/50).
- There is NO separate `generateReleaseStartupProfile` task — `./gradlew tasks --all` shows
  only `merge*StartupProfile` (which package the checked-in file). GENERATION rides the
  existing `:app:generateReleaseBaselineProfile`: the generator calls
  `BaselineProfileRule.collect(..., includeInStartupProfile = true)`, so one run re-emits
  both `baseline-prof.txt` and `startup-prof.txt` — consistent with the two files sharing
  every historical commit.
- Regenerated on the `tt_suggest_a14` emulator (API 34, 1080×2280) against the post-wave
  tree; see Gates for the result.

### 7. Autocorrect path: duplicate binary search removed
- **What**: `TdictPrefixIndex.lookup()` ran `collectExact` (which opens with
  `lowerBound(exactScratch, prefixLength, 0)`, former :513) and then
  `computeAutocorrectAdvice` (which re-ran the same `lowerBound` on the same untouched
  scratch, former :409). `exactScratch` is written exactly once per lookup (before both) and
  only ever read afterwards — verified by auditing every `exactScratch[...]` site and the
  variant generators/scanBlockRange (no writes to the query array) — so the two searches
  returned the same value. The bound is now computed once in `lookup()` and passed to both.
- **Behavior**: byte-identical; covered by the untouched `TdictPrefixIndexAutocorrectTest`
  (green).
- **ms**: one O(log n) binary search (up to 17 probes over 110 000 entries) removed per
  keystroke lookup.

### 8. Suggestion strip: one `rebuildDisplaySuggestions` per publication
- **What**: every band publication called `setSuggestions` (rebuild #1, three
  `TextUtils.ellipsize` runs) immediately followed by `setEmphasis` (rebuild #2 when the
  marker changed — the autocorrect preview band). The first rebuild's output was never drawn:
  `displaySuggestions` is read only from `onDraw`, and both calls run in one synchronous
  UI-thread stack (`SuggestionsController.showBand` publishes words and marker together —
  a contract pinned by `SuggestionStripSourceContractTest`).
- **Change**: `setSuggestions` now marks `displayRebuildPending` instead of rebuilding;
  `setEmphasis` performs the single rebuild when the marker changed OR a rebuild is pending.
  `rebuildDisplaySuggestions`/`clearDisplaySuggestions` clear the flag, so
  `onSizeChanged`/`clearSuggestions`/`release` semantics are unchanged.
- **Behavior**: byte-identical pixels and identical a11y content (state reads never moved);
  one `invalidate()` per publication as before. Zero-alloc contract tests green.
- **ms**: 3 ellipsizations + string allocs saved per preview-band publication.

### 9. `requestCurrentPrefix` duplicate-lookup shortcut
- **What**: a second `requestCurrentPrefix()` arriving while the band is still bound to the
  SAME word (PREFIX) or the SAME context (NEXT_WORD) in the SAME session re-issued an
  identical engine request. Now skipped:
  - PREFIX: `word == displayedPrefix && displayedSessionId == sessionId` — the band already
    shows this word's results. `displayedPrefix` is set only when results are actually
    displayed and cleared on every unbind, so a revisited prefix (backspace) does NOT match
    and re-requests as before; a token==null rejection resets `requestSessionId`
    (`clearToReservedBand`), so the retry path is preserved.
  - NEXT_WORD: additionally `bandHasActiveLanguageWord` — an emoji-only band
    (`displayedContextWord` set, no active-language word) must keep the
    `onCompanionBigramAttached` re-request alive, or the companion fill of the tail cells
    (audit B4) would be stranded.
- **Behavior**: the engine is asked strictly fewer, never different, questions; the band's
  contents are unchanged. Adjudicated by the full JVM suite (all SuggestionsController*,
  bigram-attach, language-switch pins green).

### 10. NEW p95 pin over the composite NEXT_WORD path
- New `TtNextWordPredictP95Test`: `CompositePrefixComputer.predict` on the real shipped
  assets (tatar dictionary + bigrams + `TatarSuffixRules` forms + global top-frequency
  fallback — the `TtNextWordFillE2ETest` wiring), probes covering every stage (bigram heads
  `сәлам`/`һәм`, form-only `сәләм`, fallback-only `сәләмә`), 500 warm-up + 2 000 samples,
  budget p95 ≤ 5 ms (the prefix-side pins' budget).
- **Measured**: see Gates.

### 11. `KeyDetector.detectHitKey`: index loop
- **What**: `for (final Key key : mKeyboard.getNearestKeys(...))` allocated an Iterator per
  call — and this runs once per gesture sample (every MOVE goes through
  `updateGlideFeedback`/hit testing). `ProximityInfo.getNearestKeys` returns an
  `unmodifiableList` view over an `ArrayList`, so indexed access is O(1): plain index loop now.
- **Memory**: one Iterator allocation removed per call; zero behavior change.

### 12. `PointerTracker.mGlidePath`: lazy allocation
- **What**: every tracker eagerly allocated a `GlidePath` (three 512-entry float arrays ≈
  6 KB) at construction — also with the glide preference off. Now null until the first
  glide-ELIGIBLE touch down (`onDownEventInternal`), reused afterwards.
- **Safety**: the decider's invariant (TRACKING/ARMED only after an eligible down) guarantees
  the buffer exists at every `addPoint`/delivery site; the contract-pinned literals
  (`mGlidePath.addPoint(x, y, (float) eventTime);`, `sListener.onGlideInput(mGlidePath);`)
  are kept verbatim. The unconditional `clear()` at down was redundant — every glide
  terminal (up/cancel/armed-cancel) already empties the buffer; the cancel path is
  null-guarded (it runs for non-glide touches).
- **Memory**: ~6 KB per never-gliding tracker (the pool grows to the max simultaneous
  pointer count ever seen).

### 13. Glide-trail fade cadence 16 → 33 ms
- **What**: `MainKeyboardView.FADE_FRAME_MS` — the post-lift fade-out of the trail
  re-invalidated at ~60 fps. The fade itself is wall-clock anchored
  (`GlideTrail.fadeFactor(nowMs)` over `FADE_OUT_MS = 250`), so the cadence changes only the
  redraw COUNT (16 → 8 frames per fade), never the duration or the alpha ramp.
- **Battery**: halves the redraw rate of a purely cosmetic animation.

### 14. `EmojiPanelView.onVisibilityChanged`: stop the fling on hide
- **What**: the hide path cancelled the delete repeat, the skin-tone popup and the gesture —
  but not the fling scroller. A panel hidden mid-fling resumed the stale fling on the next
  show (a visible jump) and carried a stale `flingActive`. Now `scroller.forceFinished(true)`
  + `flingActive = false`, the exact pair `release()`/`releaseSnapshotCaches()` already use.
- **Behavior**: the one stated change — no stale fling after re-show; everything else
  identical.

### 15. `SuggestionStripView.release()`: cancel the pending long-press
- **What**: `release()` dropped state and listeners but left a possibly-posted
  `longPressRunnable` in the queue; it would fire into a released view (finding cleared
  state — harmless but wrong). `removeCallbacks(longPressRunnable)` added.

### 16. `TimerHandler.cancelAllMessages`: remove the marker messages too
- **What**: `cancelAllMessages()` (called from `MainKeyboardView.cancelAllOngoingEvents`)
  removed key-repeat, long-press and preview-dismiss messages but left
  `MSG_TYPING_STATE_EXPIRED` and `MSG_DOUBLE_TAP_SHIFT_KEY`. Those two are never handled —
  they exist only as `hasMessages()` markers (`isTypingState`,
  `isInDoubleTapShiftKeyTimeout`) — so a leftover kept the marker stale-true until it
  expired on its own.
- **Behavior**: the stated change — the two markers are cleared with everything else.

## Deferred to the measured wave (with the analyzer's impact estimate)

The brief names six items for the later, measurement-driven wave. Where an in-tree number
exists it is quoted; the rest are deliberately unquantified here — their estimates are the
measured wave's first job, not this wave's.

- **resources.arsc compression**: the 3.0.2 APK audit measures `resources.arsc` at
  99 944 B stored uncompressed. Enabling its deflate is an aapt2-level switch, but it moves
  every resource offset and must be validated against the reproducible-build job and the
  pinned-asset gates — a pipeline change, not a byte-identical one.
- **HW partial redraw / dirty-rect drawing**: `KeyboardView` redraws through one offscreen
  buffer blit; `invalidate(rect)` plumbing could cut the per-keystroke raster work, but the
  win depends on measured overdraw (GPU profile data), not on static reading.
- **Glide index idle release**: the decoder's word inventory stays mapped for the engine's
  lifetime; releasing it at idle touches the E5c two-stage readiness and the attach/detach
  races — behavior-risking, needs the device pass.
- **Emoji index split**: `emoji_search_v1.txt` is 216 426 B and `emoji_suggest_v1.txt`
  89 318 B of assets; sharding the suggest table by first letter would cut the
  one-per-process load, but it is an asset-pipeline change (packer + new pins in
  `tests/emoji_*`), a mission of its own.
- **Vector launcher icon**: the per-density WebP launchers (5 buckets; xxhdpi alone is
  14 366 + 9 086 + 2 242 B) could collapse into one vector; deferred because icon rendering
  on old launchers needs device verification (the IconLauncherShape lint history lives here).
- **androidx.customview removal** (1.1.0, the only runtime `implementation` dependency in
  `app/build.gradle`): drops the library and its resource footprint but requires re-owning
  `ExploreByTouchHelper`'s accessibility-node plumbing in its five hosts
  (`KeyboardAccessibilityDelegate`, `MoreKeysKeyboardAccessibilityDelegate`,
  `SuggestionStripView`, `EmojiPanelView`, `EmojiSearchView`) — a11y-critical code
  that demands the measured wave's device pass, not a static wave.

# O2 — the measured wave (same day, POCO C71 device measurements)

Every item below was measured BEFORE and AFTER on the POCO C71 (25028PC03G, 720x1640,
HyperOS) with the O1 tree as the baseline build. Kept items showed no regression on their
metric; nothing regressed enough to revert. The MIUI quirk that made the protocol fiddly is
recorded here once: installing over (`adb install -r`) OR force-stopping the selected IME
package resets the default IME to the stock one — the system picker is the only assertion
that sticks, and force-stop is never used on the IME before a typing measurement.

### O2-1. resources.arsc deflate — KEPT (−73 728 B)
- **What**: `scripts/release_pack.sh` gained a step between the unsigned build and
  `zipalign -z`: a stdlib-python rewrite that flips `resources.arsc` from STORED to DEFLATED
  (content byte-identical, entry list verified identical, fail-closed). zipalign -z then
  re-lays out the archive (re-aligning the remaining STORED entries, re-zopfli-ing arsc
  itself), `zipalign -c` verifies, and the v2 signature covers the final bytes as before.
- **Bytes**: arsc 99 908 B stored → 25 545 B deflated in the signed APK; total signed size
  1 846 564 → 1 772 836 B for this item alone.
- **Device cold start** (am start -W of the setup activity, force-stop between, 5 runs each):
  BEFORE median 275 ms (265/265/275/335/415) → AFTER median 257 ms (252/256/257/264/304).
  No regression (the +10 ms kill line), if anything a small win from reading 74 KB less.

### O2-2. HW partial redraw through the offscreen buffer — KEPT (median frame −17 %)
- **What**: `KeyboardView.onDraw`'s hardware-accelerated early return is gone — the buffer +
  partial-update model now serves HW too. The old TODO ("Confirm if it's really required to
  draw all keys when hardware acceleration is on") is answered: on the frame canvas, yes —
  a partial draw there would drop every non-invalidated key from the display list. Inside the
  persistent buffer, no: the invalidated keys alone are repainted (the buffer canvas reports
  `!isHardwareAccelerated()`, so the software branch — per-key CLEAR included — applies
  verbatim; the "without the CLEAR step" of the brief refers to the frame, which the single
  drawBitmap covers whole). The two `isHardwareAccelerated` branches in `onDrawKeyboard`
  became dead and were removed with the TODO.
- **Device frames** (`dumpsys gfxinfo` framestats of the `InputMethod` window, a fixed
  32-event Tatar typing script, 120 frames per run, 3 runs each): BEFORE p50 8.2/8.2/8.3 ms,
  p90 11.4/12.0/11.4; AFTER p50 6.9/6.7/6.8 ms, p90 12.4/11.9/11.8. Median frame −1.4 ms
  (−17 %); the tail is flat within noise.
- **Visual pass on device (the hard gate)**: idle board, key press + preview popup, shift
  latch, the more-keys panel (ь → Ъ), glide trail mid-gesture and its post-lift fade, the
  spacebar language label, the emoji panel open/close — all clean; dark AND light themes
  checked. No artifact → kept.
- **Cost note**: the HW path now allocates the offscreen bitmap the SW path always had
  (~1.6 MB for a full-width board) — the frame win pays for it; it is still freed by the
  existing `deallocateMemory` on the same idle timer the O2-3/4 releases ride.

### O2-3. Glide word-index idle release — KEPT
- **What**: `LatinIME.deallocateMemory` (MSG_DEALLOCATE_MEMORY, 10 s after the keyboard
  closes) now calls `SuggestionsController.releaseGlideIndexes()`, which asks every live
  engine handle to drop its lazily built glide word index (~6 MB of pure derivation). The
  chain: `EngineHandle.releaseGlideIndex()` (default no-op, fakes compile) →
  `MappedDictionaryEngine` → `LatestOnlyPrefixEngine.releaseGlideIndex()` POSTS the drop onto
  the engine's serialized worker (the decoder is worker-confined; the UI thread only
  enqueues; a dead engine skips quietly) → `CompositePrefixComputer` →
  `GlideDecoderHost.releaseIndex()`. The next decode rebuilds the index from the dictionary.
- **Pin**: `MappedDictionaryEngineGlideTest.anIdleReleaseDropsTheIndexAndTheNextGlideRebuildsIt`
  (decode → release → decode again, identical answer; the manual executor makes the
  maintenance-task ordering deterministic).
- **Device cost of the rebuild** (instrumentation on the POCO, GlideDeviceInstrumentationTest):
  a cold decoder + first decode after a release = **730.8 ms** on the engine worker (the
  110k-entry walk over the mmap'd dictionary, mostly page-in after idle); a warm decode is
  1.1 ms (the P7-4 gate re-measured p95 3.1 ms PASS). The rebuild never touches the UI
  thread — the first glide after an idle release simply answers ~0.7 s later than warm, which
  is the same cost the pre-O2 code paid on the FIRST glide after process start. No typing
  stutter by construction.

### O2-4. Emoji indexes idle release — KEPT
- **What**: three holders released on the same deallocate pass, all lazy-reloading through
  their existing first-use paths: `EmojiPanelController.releaseSearchIndex()` (the filtered
  panel-search copy; the terminal EMPTY verdict is deliberately kept — a release never
  resurrects a dead asset), `SuggestionsController.releaseEmojiSuggest()` (drops the loaded
  table and re-arms the one-shot preparation ONLY when a source existed — a terminal failure
  stays terminal), and `SharedEmojiSearchIndex.releaseProcessWide()` (the process-wide parsed
  index; the @Volatile/synchronized discipline unchanged; the failure-terminal note amended).
- **Device reload cost** (instrumentation, EmojiIndexReloadInstrumentationTest): search-index
  re-parse **216.0 ms** (1 389 entries); suggest-table parse + glyph probe **202.1 ms**
  (3 976 entries kept of 447 drawable) — both on background executors, never the UI thread,
  once per idle cycle.
- **Device behavior cycle**: with the release build — type сәлам+space → strip tail 👋;
  panel → search "сул" → results; hide the keyboard 12 s (the deallocate fires at 10 s);
  reopen; repeat — the 👋 band and the search results come back identical. Screenshots
  recorded.

### O2-5. Launcher icon vectorization — KEPT (−62 602 B of WebP)
- **What**: the five densities of `ic_launcher_foreground.webp` + `ic_launcher_monochrome.webp`
  (62 602 B total, STORED uncompressed in the APK) are replaced by two VectorDrawables in
  `res/drawable/`, and `mipmap-anydpi-v26/ic_launcher.xml` points at them. The legacy
  `ic_launcher.webp` set stays (pre-API-26 launchers; minSdk is 24).
- **How the vectors were made (honest note)**: the brief assumed `icons/icon.svg` is the
  current icon's source — it is the SUPERSEDED "Simple" icon (blue badge; its text paths were
  the `icon_launcher_text` string O1 deleted). The current green keyboard+bubble icon exists
  only as raster masters, and the pre-babb7d28 vector drawables were the old design too. The
  vectors were therefore TRACED from the 324x324 xxhdpi masters: per-color masks (the two
  greens sampled from the master: #04A14D frame/outline/glyph, #51CE7B keys; the bubble's
  white is the #FEFEFE adaptive background showing through, as before), `potrace` with
  speckle suppression, then a potrace-SVG → VectorDrawable transform (y-flip + 324px→108dp
  scale, 2-decimal precision). The dark layer is 2 compound paths, the keys 11, the
  monochrome silhouette 2.
- **Visual parity on device**: the MIUI app-info squircle (POCO, 320 dpi) and the AOSP
  circle (emulator, 440 dpi) render the vector identically to the WebP before-shot —
  geometry, colors and the ә glyph all match by construction and by eyeball. The monochrome
  layer is a faithful silhouette trace (no themed-icon launcher here to render it; the trace
  is the master's exact alpha mask).

### O2-6. androidx.customview removal — KEPT (the last runtime dependency is gone)
- **What**: `implementation 'androidx.customview:customview:1.1.0'` dropped from
  app/build.gradle. The five `ExploreByTouchHelper` hosts now extend
  `rkr.simplekeyboard.inputmethod.compat.ExploreByTouchHelper` — a fork of the exact 1.1.0
  source (AOSP, Apache-2.0, attribution header), ported to framework APIs at minSdk 24:
  SparseArrayCompat→android.util.SparseArray, AccessibilityDelegateCompat→View.AccessibilityDelegate,
  NodeProviderCompat→AccessibilityNodeProvider, NodeInfoCompat→AccessibilityNodeInfo,
  *EventCompat/*RecordCompat→the framework classes, ViewCompat.*→the direct View calls.
  `FocusStrategy` is forked beside it (the framework's own FocusStrategy is API 26+).
  One deliberate deviation, documented in code: the androidx original walked the
  virtual-parent chain via `AccessibilityNodeInfoCompat.mParentVirtualDescendantId`, which
  the framework class does not expose — that walk was dead code in the 1.1.0 shape (the
  helper only ever parents virtual children straight to the host, so the id was always
  HOST_ID and the loop never ran); the fork elides it.
- The `ViewCompat.setAccessibilityDelegate`/`isAttachedToWindow` calls became the direct
  View calls (API 14/19), `AccessibilityNodeInfoCompat` constants became the framework
  constants (identical values), and the 12 `@Keep` markers were dropped (documentation-only:
  proguard-rules.pro states nothing needs keeping, verified by the R8 release build + the
  suite). Pinned source contracts were amended, not weakened:
  `EmojiPanelAccessibilitySourceContractTest` now pins the fork import AND the ABSENCE of the
  dependency in build.gradle; the strip and personal-forget pins assert the same actions on
  the framework constants.
- **Verification**: full JVM suite 1 588/0; the fork compiles standalone against
  android.jar (fail-closed javac pass); on-device TalkBack pass on the POCO (TalkBack
  enabled): typing works through the text-entry fast path, strip cells commit, no crash in
  the IME process during the whole pass. Hover-explore and double-tap-activate are not
  reachable via `input tap` on this TalkBack+MIUI combination (touches pass through to the
  IME as Gboard-style direct typing); the a11y tree read side ran continuously with TalkBack
  enabled. TalkBack was left OFF afterwards.
